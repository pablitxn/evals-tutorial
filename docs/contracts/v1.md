# Frozen v1 integration contract

Status: implementation contract 1.0.0. ET-INTEGRATOR is sole schema/manifest writer.
Authority: `packages/contracts/schema/v1.json`; generated TS and Python types are
checked in and verified with `npm run contracts:check`. Request schema changes
through parent/integrator before changing consumers. No producer edits shared files.

## Imports and runtime validation

```ts
import type { EvalInput, EvalResult, Dataset, Exercise, RunRecord } from '@evals-tutorial/contracts';
import { validateContract, LIMITS } from '@evals-tutorial/contracts';
import type { EvalContext, JudgeBroker, TutorialServices } from '@evals-tutorial/contracts/services';
import { sha256, datasetHash, reviewBindingHash } from '@evals-tutorial/contracts/node';
export async function evaluate(row: EvalInput, ctx: EvalContext): Promise<EvalResult> { /* learner implementation */ }
```

Python: `from tutorial_contracts import validate_contract, dataset_hash` and
`from tutorial_contracts.generated import AgentRequest, AgentResponse`. Root
installation adds `packages/contracts/python` to the local venv. Python 3.12.
Generated type declarations are convenience; validate all runtime boundaries.

Normalized results: pass exactly 1, fail exactly 0, partial strictly between.
Per-criterion rubric owns any aggregation to a single result. Operational errors
never become scores. Fixture expectations use allowedLabels/minScore/maxScore and
requiredEvidence; the harness validates minScore <= maxScore and references.

Dataset identity: contentHash excludes only top-level contentHash; document
manifest path and SHA are included. Canonicalization is RFC 8785, pinned to canonicalize 2.1.0 (TS) and rfc8785
0.1.4 (Python), with cross-runtime tests. Canonical data rejects numeric magnitudes
above 2^53-1 for portable parsing and requires finite JSON values. All content is synthetic. C2/C3 share the same document manifest.
Exercise-specific input/output/expected JSON Schemas live in Exercise fields;
ET-WP-04 owns their values. They must be checked at the content/agent boundaries.

## Content handoff (ET-WP-04)

Write `content/tutorial.json` matching Tutorial: exactly eight Exercise records,
ordered intro, 01 through 06, and read-only 07-spec-regression. Stable IDs are the ExerciseId enum. It embeds
lessonMarkdown, starterSource, pythonSource, criteria, version/hash references,
agent variants, three domain schemas and official links. Authoring files may live
under content/intro and content/exercises/<id>; tutorial.json is the served view.
Write datasets at `content/datasets/<datasetId>/<datasetVersion>.json` matching
Dataset. Document manifests and files are beneath content/documents, paths relative
to content. Use PNG as the first portable document input; PDF capability is separate.
No references/fixtures may enter AgentRequest. UI document URLs will be
`/api/documents/<documentId>` resolved through the verified manifest, never paths.
`contentHash` is hash of the canonical dataset preimage. Document manifest SHA is
SHA-256 of exact UTF-8 file bytes, and document SHA is exact file bytes.

## Provider / agent handoff (ET-WP-05)

Own apps/agents/src/** and tests, server providers/** and judge-broker/**.
Implement `AgentService.invoke` and `JudgeBroker.bind` from services export.
Python entrypoint: `python -m tutorial_agents` consumes one AgentRequest JSON line
on stdin and returns one AgentResponse JSON line on stdout; diagnostics on stderr.
No server/listening port needed for Python. Supervisor supplies only allowlisted
profile env and resolved document paths. Its process boundary is not a sandbox.
No expected/fixtures/source in request. traceparent/tracestate are optional trusted
context. deadlineMs is a duration, at most 60000. Real failures use AgentFailure.

Global env: TUTORIAL_PROVIDER=openai|azure_foundry, TUTORIAL_MODEL,
TUTORIAL_API_KEY, optional TUTORIAL_AZURE_ENDPOINT/TUTORIAL_API_VERSION.
No per-role model overrides. Azure key-based resource endpoint only initially;
Foundry project endpoints are unsupported unless separately proved. Profile changes
change configRevision from non-secret routing fields; do not hash the key.
JudgeBinding is host-created per immutable row and lifetime budget. `judge` accepts
only rubric/criterionIds. Code disables it; Mixed permits <=2 calls per row, <=2048
output tokens/call, zero automatic retries, deadline+AbortSignal enforced. Never
accept a worker-selected endpoint/model/tool/row. Review uses a separate bounded
broker operation; its exact internal prompt API can be requested additively.
The host-only optional `JudgeBinding.fixtureId` identifies the installed fixture;
budgets are scoped by run, example and fixture, with an absent fixture ID reserved
for a real-agent row. Rebinding the same identity cannot replace its immutable
material/deadline or replenish calls. Fixture identity is not added to worker RPC.

## Runner handoff (ET-WP-06)

Own packages/evaluator-runtime/** and server validation/runs/runner/**. Implement
ValidationService and RunService; root HTTP injects them. Preferred export factory
`createRunnerServices(...)` returning `{ validation, runs }` from runs/index.ts;
list exact dependencies in handoff for integrator wiring. Do not edit HTTP/bootstrap.
Learner import allowlist: types from @evals-tutorial/contracts and
@evals-tutorial/contracts/services only. Compiler receives a fixed virtual SDK,
not this host package or repository. Worker JSONL uses JudgeRpcRequest/Response;
protocol is bounded to 1 MiB and stdout is protocol-only. IDs/bindings/call budget
must be checked host-side. No sockets, keys or .env in worker.
Docker execution must be non-root, network none, read-only, caps dropped,
no-new-privileges, bounded memory/PIDs/CPU/tmpfs. No process/VM fallback. Missing
Docker means isolation_unavailable, no submitted-code execution. Validation must
complete before provider calls. Same requestId is idempotent; conflicting payload
under reused ID returns conflict. Preserve snapshots and cancelled/late results.

## HTTP/UI handoff (ET-WP-08)

One loopback origin at http://127.0.0.1:3000. No CORS. Polling only.
GET /api/tutorial -> Tutorial; GET /api/exercises/:id/dataset -> Dataset;
GET /api/status -> ServiceStatus. GET /api/documents/:id -> allowlisted bytes.
POST /api/validate ValidateRequest -> ValidationResult.
POST /api/runs RunRequest -> 202 AcceptedRun; GET /api/runs/:id -> RunRecord;
POST /api/runs/:id/cancel {} -> RunRecord.
POST /api/reviews ReviewRequest -> 202 AcceptedReview;
GET /api/reviews/:id and POST /api/reviews/:id/cancel {} -> ReviewRecord.
Errors: ErrorResponse with non-2xx HTTP. Missing implementations return honest
503 not_implemented. Navigation/status never invoke inference. No invented links.

Use SourceSnapshot for validation/runs/review. Edits change SHA-256 of exact UTF-8
source bytes; do not trim/normalize. Version-keyed localStorage and stale status are
UI concerns; backend snapshots remain immutable. Run.status and telemetryStatus
are separate. A failed score can accompany completed execution. Undefined Phoenix
links mean unavailable, not a guessed URL. Review status stale is derived by the
UI comparing current binding, not a rewrite of historical ReviewRecord.

## Phoenix and review (ET-WP-07/09)

Phoenix owns packages/phoenix/** and server telemetry/**; expose an adapter that
accepts existing immutable Dataset/RunRecord and reads back IDs/links. Do not
repeat inference to retry telemetry. Root Compose and SDK manifests stay integrator
owned. Return actual pinned dataset version and verified links or typed failure.

Review owns packages/review/** and server review/**; implement ReviewService.
Derive ReviewBinding from stored receipts, not browser-asserted evidence. Match
validated source, discriminating fixtures and completed agent run. Binding includes
rubric/data/source, receipt digests, agent and provider configuration. Code is data;
no import/execution/tools. ReviewAssessment is model output, wrapper supplies IDs,
binding/timestamps. Stale late replies cannot complete changed source. Operational
errors are separate. Explicit retry has a new requestId and may consume tokens.

## Browser validation and Phoenix opaque IDs (2026-10-14 correction)

Wire validators are generated ahead of time from the same authoritative schema by
`scripts/generate-validators.mjs`. `validateContract` requires no dynamic string
compilation, so production `script-src 'self'` remains intact. Trusted server-side
`validateDomain` retains lazy Ajv compilation; arbitrary learner schemas are not
accepted. Run `npm run contracts:generate` after schema edits and
`npm run contracts:check` to detect drift.

Only `PhoenixLinks.datasetId`, `datasetVersionId`, and `experimentId` also admit
the base64 alphabet and up to two trailing padding characters returned by Phoenix
20.21.3. They remain bounded opaque IDs, preserved exactly, never decoded into
application identities or used as unescaped filesystem paths. Tutorial IDs,
trace IDs and loopback URL restrictions are unchanged. The final negative
lookahead enforces absolute end of input in both JavaScript and Python (a plain
`$` can match before a final newline). V1 shape and generated field types remain
unchanged; this is an additive accepted-value correction.

## Explicit telemetry retry (2026-10-14 integration addition)

`POST /api/runs/:runId/telemetry` accepts exactly `{}` and returns HTTP 202 with
RunRecord. It queues recording of a terminal immutable execution receipt only;
no agent, evaluator, judge or review is rerun. GET the same run until
telemetryStatus is recorded/failed. The optional host-only
TutorialServices.recordRun seam keeps existing producer RunService unchanged.
A recorded run is idempotent. Pending work is serialized; interrupted recordings
are recovered as failed and need an explicit retry. UI consumers may offer a
Retry recording button for failed/not_requested terminal receipts with rows.
The distribution command is `npm run telemetry:retry -- RUN_ID`.

## Review feedback language (2026-10-14 additive localization)

ReviewRequest and ReviewRecord optionally carry `feedbackLocale: "en" | "es"`.
Omitted requests default to English; older records without the field remain valid
and their feedback language is unknown. New records capture the requested locale.
The immutable request fingerprint includes it: changing locale with a reused
requestId conflicts. A new review still requires an explicit action and new ID.

Locale is presentation metadata outside ReviewBinding. It does not change the
rubric, source/data/receipt hashes, scoring, eligibility, provider profile, budget,
cancellation or late-evidence checks. ReviewBrokerBinding carries the validated
locale into trusted system instructions for summary/feedback/nextAction only;
evidence stays an exact original-language quote. The educational fallibility
notice uses the requested locale. Language compliance by the model is best effort,
not a validated fact. UI labels therefore say requested feedback language.

Switching UI language retains work and evidence and performs no inference or
translation of stored feedback. Raw diagnostics, JSON, evaluator explanations,
fixture rationale and source code are original evidence. Spanish lesson overlays
are presentation-only and never enter snapshots or review rubric material.

## Final guided specification example (2026-10-19 addition)

`07-spec-regression` appends a read-only prepared example after the six editable
cases. It uses the existing run, provider, isolation and telemetry interfaces with
one normal dataset and two fixed variants, `baseline` and `omit-fees`. The latter
is deliberately regressing and must be labeled before execution. No agent or
evaluator is generated, and navigation performs no inference.

`EvalResult.criteria` optionally carries bounded `CriterionResult` records using
the same score/label rules plus `criterionId`. Existing results remain valid.
The final prepared evaluator reports all six requirement IDs R1-R6 and a binary
aggregate (pass only if every requirement passes). The run boundary validates
that these IDs and scores match the installed rubric. Operational failures remain
row errors without evaluation scores. Phoenix retains the immutable row result.

A comparison pairs explicitly selected baseline and candidate agent receipts with
identical snapshots, evaluator hash, dataset hash, provider configuration and
repository provenance. Only completed scored rows establish pass-to-fail
regressions; missing/error rows are not compared. A new baseline starts a new
pair, retaining the prior evidence separately.
